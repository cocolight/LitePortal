# ADR-0001: 采用 ADR 记录架构决策

- **状态**：accepted
- **日期**：2026-10-05
- **决策者**：cocolight

## 背景

LitePortal 由多执行者（多个 AI 编码助手 / 多名开发者）分模块推进。此前代码里有若干「为什么这么做」的关键决定（环境变量加载顺序、bundle 打包链路、生产环境依赖迁移建表等），但只存在于代码注释与开发者记忆里：

- 新接手的人（以及 AI 助手）看到 `config.module.ts` 里奇怪的 `envFilePath` 数组顺序，无从得知这是有意为之；
- 每次想改动，都得重新推导一遍原始动机，容易误删看似冗余实则关键的步骤。

需要一个轻量、可回溯的载体记录这些决策。

## 决策

采用 **ADR（Architecture Decision Record）** 机制：

- 决策记录放在 `docs/adr/`，文件名 `NNNN-短横线小标题.md`；
- **只追加不修改**，已 accepted 的记录不可篡改；变更时新增一条 ADR 并在其中标注取代关系；
- 每条记录包含：背景、决策、理由、后果；
- AI 助手的规则由 `AGENTS.md` 引用本目录；AGENTS.md §4 红线第 5 条明确禁止修改已接受记录。

## 理由

- ADR 是纯 Markdown，无需额外工具，对已有仓库零侵入。
- 「只追加」保证了可回溯性——这是决策记录区别于普通文档的唯一价值。
- 本仓库已有三层 config 分层、多链路产物打包等高风险改动点，事前记录可显著降低「改坏却不知道为什么」的成本。

## 后果

**正面**

- 关键决策可回溯，新成员 / AI 助手能自取上下文。
- 与 `AGENTS.md`、`docs/architecture.md`、`docs/configuration.md` 形成统一的「事实源」，减少文档漂移。

**负面**

- 每次重要改动需额外维护一条记录，有写作成本。
- 若团队不遵守「只追加」，价值会迅速归零（靠 `AGENTS.md` 红线约束）。
